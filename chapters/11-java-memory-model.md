# Java Memory Model: вся суть на одной странице

> Видимость, порядок, атомарность и happens-before без лишней теории

← [Почему изменения нужно «увидеть»](./10-visibility.md) · [Happens-before простыми словами](./12-happens-before.md) →

**Java Memory Model (модель памяти Java), или JMM**, — часть спецификации Java, которая отвечает на один вопрос:

> Какие значения разрешено увидеть потоку, когда с общей памятью работают несколько потоков?

JMM — не сборщик мусора, не устройство heap и не алгоритм JVM. Она задаёт правила, которые обязаны соблюдать компилятор, JIT и процессор. Благодаря этому правильно синхронизированная Java-программа имеет предсказуемый смысл на разных компьютерах.

```text
Java-код
   ↓
JMM: какие результаты допустимы
   ↓
JIT и CPU: как угодно оптимизируют код,
но не нарушают эти гарантии
```

## Три проблемы, которые нужно различать

| Проблема | Простой вопрос | Пример |
|---|---|---|
| **Atomicity (атомарность)** | Может ли другой поток вклиниться в операцию? | `count++` состоит из чтения, сложения и записи |
| **Visibility (видимость)** | Обязан ли поток увидеть чужую запись? | один поток написал `ready = true`, другой всё ещё читает `false` |
| **Ordering (порядок)** | Могут ли операции наблюдаться в другом порядке? | другой поток увидел `ready == true`, но не увидел записанные перед ним данные |

Это независимые свойства. Например, чтение и запись `volatile int` атомарны и видимы, но выражение `count++` всё равно не становится одной атомарной операцией.

## Почему исходного порядка кода недостаточно

Внутри одного потока Java сохраняет поведение программы так, будто инструкции выполнялись по порядку. Это называют **as-if-serial semantics (семантика «как если бы последовательно»)**.

Но JIT и процессор вправе переупорядочить независимые операции. Один поток разницы не заметит, а другой без синхронизации может увидеть промежуточное состояние.

```java
int value = 0;
boolean ready = false;

// Поток A
value = 42;
ready = true;

// Поток B
if (ready) {
    System.out.println(value); // без связи между потоками нет нужной гарантии
}
```

Ошибка здесь не в кеше конкретного процессора. Ошибка в том, что программа не создала предусмотренную JMM связь между записью и чтением.

## Главное правило: happens-before

**Happens-before (отношение «предшествует»)** — гарантия передачи результатов одного действия другому.

Если действие A *happens-before* действию B, то:

1. результаты A обязаны быть видимы в B;
2. A наблюдается до B с точки зрения программы.

```text
записи данных в потоке A
          ↓
     release-действие
          ║  happens-before
     acquire-действие
          ↓
чтение данных в потоке B
```

Здесь **release (освобождение)** публикует предыдущие изменения, а соответствующий **acquire (получение)** делает их доступными читающему потоку. В Java разработчик обычно не ставит барьеры памяти вручную — нужную связь создают языковые конструкции и библиотеки.

## Что создаёт happens-before

| В потоке A | Связь | В потоке B |
|---|---|---|
| выход из `synchronized(lock)` | на том же объекте `lock` | последующий вход в `synchronized(lock)` |
| запись в `volatile`-поле | для того же поля | последующее чтение этого поля |
| действия до `thread.start()` | передаются запущенному потоку | первые действия нового потока |
| все действия потока | передаются ожидающему | успешный возврат из `thread.join()` |
| запись до завершения задачи | через контракт библиотеки | получение результата из `Future.get()` |

Также действуют два общих правила:

- **program order (порядок программы):** более раннее действие потока happens-before более позднего действия того же потока;
- **transitivity (транзитивность):** если A happens-before B, а B happens-before C, то A happens-before C.

Следующая глава разбирает эти связи подробнее.

У `final`-полей есть отдельная гарантия инициализации: если ссылка на объект не утекла из конструктора, другой поток, получивший эту ссылку, увидит корректно сконструированные значения `final`-полей. Это специальное правило JMM, а не ещё одна строка обычного happens-before.

## Исправляем пример через volatile

```java
int value = 0;
volatile boolean ready = false;

// Поток A
value = 42;       // 1
ready = true;     // 2: volatile write

// Поток B
if (ready) {      // 3: volatile read
    System.out.println(value); // 4: гарантированно 42
}
```

Получается цепочка:

```text
1 → 2 → 3 → 4
```

- `1 → 2` и `3 → 4` следуют из порядка программы;
- `2 → 3` — правило записи и чтения одного `volatile`-поля;
- значит, по транзитивности `1 → 4`, и значение `42` видно потоку B.

`volatile` здесь подходит, потому что один поток публикует готовые данные, а другой их читает. Если оба потока делают составное изменение вроде `count++`, нужны `AtomicInteger`, `synchronized` или другой инструмент атомарного обновления.

## Data race и правильно синхронизированная программа

**Data race (гонка данных)** возникает, когда два потока обращаются к одной переменной, хотя бы один пишет, а действия не упорядочены через happens-before.

```text
одна переменная + разные потоки + хотя бы одна запись
                    + нет happens-before
                    = data race
```

Для **правильно синхронизированной программы** без гонок данных JMM даёт сильную практическую гарантию: её выполнение выглядит **sequentially consistent (последовательно согласованным)** — как некоторое чередование действий потоков, сохраняющее порядок каждого потока.

Это не означает, что потоки реально исполняются последовательно. Это означает, что результат можно объяснить допустимым последовательным чередованием.

## Что выбрать на практике

| Задача | Обычно подходит |
|---|---|
| опубликовать флаг или неизменяемое состояние | `volatile` |
| атомарно обновить один счётчик | `AtomicInteger`, `AtomicLong`, иногда `LongAdder` |
| защитить несколько связанных полей и инвариант | `synchronized` или `Lock` |
| передавать задачи и результаты | `ExecutorService`, `Future`, concurrent collections |
| опубликовать неизменяемый объект | корректный конструктор, `final`-поля и безопасная публикация |

Лучше выбирать высокоуровневый инструмент, контракт которого уже создаёт необходимые гарантии, а не пытаться рассуждать о кешах и memory barrier для каждой строки.

## Частые ошибки на собеседовании

### «volatile делает операцию атомарной»

Нет. `volatile` даёт видимость и порядок для работы с полем, но не склеивает read-modify-write операцию:

```java
volatile int count;
count++; // всё ещё read → add → write
```

### «synchronized нужен только для взаимного исключения»

Нет. Выход из монитора публикует сделанные изменения, а следующий вход в тот же монитор их получает. Важно, что монитор должен быть **тем же объектом**.

### «happens-before означает раньше по времени»

Нет. Это отношение, заданное спецификацией. Операция может физически произойти раньше, но без happens-before другой поток не получает гарантии видимости.

### «каждый поток хранит отдельную копию heap»

Нет. Heap общий. Регистры, кеши и оптимизации влияют на наблюдаемое поведение, но JMM описывает гарантии через действия программы, а не через упрощённую модель «главной памяти» и отдельных копий.

## Ответ про JMM за 40 секунд

> JMM — часть спецификации Java, которая определяет допустимые результаты многопоточного выполнения: когда записи одного потока обязаны быть видимы другому и какой порядок действий гарантирован. Три связанные проблемы — atomicity, visibility и ordering. Основной инструмент рассуждения — happens-before. Его создают, например, один монитор `synchronized`, запись и чтение одного `volatile`-поля, `Thread.start()`, `Thread.join()` и контракты concurrent-библиотек. Если конфликтующие обращения не связаны happens-before, возникает data race, и полагаться на наблюдаемый порядок нельзя.

## Как разобрать любой пример

1. Найди общие изменяемые данные.
2. Отметь все чтения и записи из разных потоков.
3. Найди синхронизирующие действия: `volatile`, один monitor, `start`, `join`, concurrent API.
4. Построй цепочку happens-before от записи к чтению.
5. Если цепочки нет — гарантии видимости нет.
6. Отдельно проверь, не является ли операция составной, например `++`, `check-then-act` или `get` + `put`.

## Самопроверка

1. Делает ли `volatile` выражение `counter++` атомарным?
2. Передаёт ли выход из `synchronized(a)` видимость входу в `synchronized(b)`?
3. Почему запись обычного поля перед записью `volatile`-флага становится видна после чтения флага?
4. Чем data race отличается от race condition?

<details>
<summary>Ответы</summary>

1. Нет: это три действия — чтение, сложение и запись.
2. Нет, если `a` и `b` — разные объекты.
3. Из-за порядка программы, volatile happens-before и транзитивности.
4. Data race — формальное отсутствие happens-before между конфликтующими доступами; race condition — более широкая логическая зависимость результата от порядка событий.

</details>
