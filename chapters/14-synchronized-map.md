# synchronizedMap: Map с одним общим lock

> Простая синхронизированная обёртка и границы её применения

← [Когда одного счётчика мало](./13-shared-map.md) · [Какие конкурентные коллекции есть в Java](./15-concurrent-collections-overview.md) →

## Что делает synchronizedMap

`Collections.synchronizedMap()` создаёт потокобезопасную обёртку над `Map`. Все операции через эту обёртку используют один общий lock: пока один поток работает с map, остальные ждут освобождения lock.

## Когда появился и устарел ли

`Collections.synchronizedMap()` появился в JDK 1.2 в 1998 году вместе с Java Collections Framework. Это старый API, но не deprecated (не объявленный устаревшим): он по-прежнему входит в современную Java и имеет подходящие сценарии применения.

В Java 5 в составе JSR 166 появились `ConcurrentMap` и `ConcurrentHashMap`. Для общей изменяемой map, к которой часто обращаются несколько потоков, `ConcurrentHashMap` обычно служит современным выбором по умолчанию: она лучше поддерживает параллельный доступ и предоставляет атомарные операции для отдельного ключа.

Это не означает, что `synchronizedMap` нужно всегда заменять. Она остаётся полезна, когда нужен один общий lock, согласованная операция над всей map или синхронизированная обёртка над конкретной реализацией — например, `LinkedHashMap`. Поэтому выбирать следует не по возрасту API, а по требуемому контракту и характеру нагрузки.

## Задача перед теорией: небольшой реестр настроек

Представь внутренний инструмент, где несколько потоков читают и изредка меняют небольшой набор runtime-настроек:

```java
Map<String, String> settings =
    Collections.synchronizedMap(new HashMap<>());
```

Условия задачи:

- элементов несколько десятков;
- обращений немного;
- максимальный throughput не критичен;
- требуется обычный интерфейс `Map`;
- иногда нужен согласованный обход всех настроек;
- простой протокол важнее высокой параллельности.

Для такого случая `synchronizedMap` может быть разумным выбором.

Но для реестра миллионов загрузок, к разным ключам которого постоянно обращаются многие потоки, один общий lock станет точкой конкуренции. Там обычно лучше `ConcurrentHashMap`.

## Где находится synchronizedMap

Это static factory method (статический фабричный метод) класса `java.util.Collections`:

```java
import java.util.Collections;
import java.util.HashMap;
import java.util.Map;

Map<String, Integer> views =
    Collections.synchronizedMap(new HashMap<>());
```

Метод не превращает исходный объект `HashMap` в concurrent collection. Он возвращает wrapper (обёртку), которая синхронизирует доступ к исходной map.

```text
caller
  ↓
synchronized wrapper ── держит mutex ──→ HashMap
```

Поэтому исходную ссылку нельзя продолжать использовать напрямую:

```java
Map<String, Integer> raw = new HashMap<>();
Map<String, Integer> safe = Collections.synchronizedMap(raw);

safe.put("car:1", 1); // через общий lock
raw.put("car:2", 2);  // обходит wrapper — протокол сломан
```

После создания все обращения должны идти через `safe`.

## Как устроена синхронизация

Операции обёртки захватывают один общий mutex:

```text
Thread 1: get("car:123") → держит LOCK
Thread 2: put("car:456") → ждёт LOCK
Thread 3: remove("car:789") → ждёт LOCK
```

Ключи разные, но lock один. Это даёт простой контракт: отдельные операции map не выполняются одновременно.

Плюс — корректность легко объяснить. Минус — независимые операции мешают друг другу, поэтому при высокой нагрузке wrapper может стать contention point (точкой конкуренции).

## Какие гарантии она даёт

Если вся работа идёт через возвращённую обёртку:

- отдельные вызовы `get()`, `put()`, `remove()` и других методов защищены общим mutex;
- изменения безопасно публикуются между потоками через monitor;
- backing map (внутренняя map) сохраняет свои обычные свойства, например порядок или разрешение `null`;
- несколько действий можно объединить одной внешней синхронизацией на wrapper.

Последний пункт полезен, но требует явного кода.

## Отдельные безопасные вызовы не делают композицию атомарной

Каждый вызов безопасен отдельно:

```java
if (!settings.containsKey(key)) {
    settings.put(key, value);
}
```

Но вся последовательность check–then–act (проверить, затем действовать) не атомарна:

```text
Thread 1: containsKey → false
Thread 2: containsKey → false
Thread 1: put(valueA)
Thread 2: put(valueB)
```

Если нужен составной протокол, весь он должен выполняться под mutex обёртки:

```java
synchronized (settings) {
    if (!settings.containsKey(key)) {
        settings.put(key, value);
    }
}
```

Для простого добавления лучше использовать одну атомарную операцию API, например `putIfAbsent()` или `computeIfAbsent()`, если её контракт точно совпадает с задачей.

Внешний `synchronized` особенно полезен, когда нужно согласованно проверить или изменить несколько элементов одной map. Цена — на всё время составной операции блокируются остальные обращения через wrapper.

## Почему обход требует внешнего synchronized

Этот код небезопасен:

```java
for (Map.Entry<String, String> entry : settings.entrySet()) {
    use(entry);
}
```

Получение `entrySet()` — один вызов, а итерация состоит из многих последующих действий. Между ними другой поток может изменить map.

Документация требует вручную синхронизироваться на возвращённой map:

```java
synchronized (settings) {
    for (Map.Entry<String, String> entry : settings.entrySet()) {
        use(entry);
    }
}
```

Так весь обход видит состояние под одним общим lock. Но если `use(entry)` выполняет медленный I/O или неизвестный callback (обратный вызов), lock будет удерживаться слишком долго.

Безопаснее сначала сделать snapshot (снимок), затем обрабатывать его без lock:

```java
Map<String, String> snapshot;
synchronized (settings) {
    snapshot = new HashMap<>(settings);
}

for (Map.Entry<String, String> entry : snapshot.entrySet()) {
    use(entry);
}
```

## Когда synchronizedMap стоит выбирать

### 1. Маленькая map и низкая конкуренция

Если потоков мало, обращения редкие, а критические секции короткие, преимущество более сложной concurrent implementation может быть неважно.

```text
несколько потоков
+ десятки элементов
+ редкие операции
+ нет требования к высокой пропускной способности
→ synchronizedMap достаточно
```

### 2. Нужен самый простой общий протокол

Один mutex легче проверять: в каждый момент с map работает один поток. Это подходит небольшому компоненту, где простота и доказуемость важнее параллельности.

### 3. Нужно атомарно выполнить произвольную последовательность

Wrapper предоставляет естественный объект для внешней синхронизации:

```java
synchronized (settings) {
    validateWholeMap(settings);
    updateSeveralEntries(settings);
}
```

`ConcurrentHashMap` даёт сильные атомарные операции для отдельного ключа, но не превращает произвольную операцию над всей map в транзакцию.

### 4. Нужна согласованная копия всей map

Под общим lock легко создать snapshot без конкурентных изменений:

```java
Map<K, V> snapshot;
synchronized (map) {
    snapshot = new HashMap<>(map);
}
```

Это может быть полезно для небольшой конфигурации или формирования диагностического ответа.

### 5. Нужно обернуть существующую реализацию Map

Например, нужен порядок вставки `LinkedHashMap`:

```java
Map<String, Value> ordered = Collections.synchronizedMap(
    new LinkedHashMap<>()
);
```

Или нужен custom map (собственный тип map), для которого нет специализированного concurrent-аналога. Все ссылки на backing map при этом должны оставаться внутри компонента.

### 6. Legacy API требует обычный Map

Legacy code (унаследованный код) может ожидать `Map`, выполнять короткие операции и не нуждаться в специальных weakly consistent iterators. Синхронизированная обёртка позволяет добавить простой общий lock без полной переработки компонента.

Но тип `Map` принимает и `ConcurrentHashMap`, поэтому одно только требование интерфейса ещё не является причиной выбрать wrapper. Важен нужный контракт.

## Когда synchronizedMap выбирать не стоит

### Высокая конкуренция по независимым ключам

```text
тысячи requests
→ разные keys
→ каждый get/put ждёт один mutex
```

Для такого реестра обычно подходит `ConcurrentHashMap`: она проектировалась для конкурентных чтений и обновлений.

### Долгий обход или callback под lock

Пока один поток делает медленный обход, все остальные операции стоят. Делай короткий snapshot либо выбирай коллекцию с подходящим iterator contract.

### Producer–consumer

`synchronizedMap` не умеет ждать появления элемента и не создаёт backpressure (обратное давление). Для передачи работы используют `BlockingQueue`, а не map с метафорической «очередью к lock».

### Нужны weakly consistent iterators

Итераторы concurrent collections допускают конкурентные изменения и не требуют блокировать всю структуру. У wrapper обход защищают внешним `synchronized` либо копией.

### Нужны атомарные операции для горячих ключей

`ConcurrentHashMap.compute()`, `merge()` и `computeIfAbsent()` позволяют выразить обновление одного ключа без глобального mutex для всей map. Их точные границы разобраны в уроке про [безопасность `computeIfAbsent()`](./17-compute-if-absent-safety.md).

### Нужна сортировка и диапазоны под нагрузкой

Рассмотри `ConcurrentSkipListMap`. `synchronizedMap(new TreeMap<>())` сохраняет сортировку, но сериализует все операции одним lock.

## Сравнение с ConcurrentHashMap

| Вопрос | `synchronizedMap` | `ConcurrentHashMap` |
|---|---|---|
| Синхронизация | один общий mutex | конкурентный доступ, координация на более узких участках |
| Параллельные чтения | сериализуются общим mutex | рассчитана на конкурентные чтения |
| `null` | зависит от backing map | запрещён для keys и values |
| Обход | внешний `synchronized` | weakly consistent iterator |
| Составная операция всей map | можно явно закрыть общим mutex | отдельная внешняя координация |
| Атомарное обновление одного key | возможно, но под общим lock | специализированные `compute`, `merge`, `putIfAbsent` |
| Сложность протокола | низкая | нужно понимать контракт конкретных операций |
| Типичный масштаб | малая конкуренция | частый конкурентный доступ |

`ConcurrentHashMap` не «лучше вообще». Например, она не допускает `null` и не даёт простой транзакции всей map. Но для типичного многопоточного реестра по ключу она масштабируется лучше.

## Сравнение с неизменяемой Map

Если map полностью заполнили до того, как её начали использовать несколько потоков, и после этого больше не изменяют, потокам можно одновременно читать её без дополнительной синхронизации. Чтения не меняют общее состояние и потому не мешают друг другу.

Для конфигурации удобно создать неизменяемую копию:

```java
Map<String, String> settings = Map.copyOf(loadedSettings);
```

Последующие изменения `loadedSettings` не затронут `settings`, а вызовы `settings.put()` и `settings.remove()` завершатся с `UnsupportedOperationException`. Копирование при этом неглубокое: если values сами изменяемы, для них всё равно нужен собственный потокобезопасный протокол.

Одной неизменяемости недостаточно: остальные потоки должны гарантированно получить уже полностью созданную map. Safe publication (безопасная публикация) — это передача ссылки между потоками способом, который создаёт нужную [happens-before связь](./12-happens-before.md). Благодаря ей читающий поток видит все записи, сделанные при создании map.

Например, инициализация `static final` поля безопасно публикуется правилами инициализации класса:

```java
private static final Map<String, String> SETTINGS =
    Map.copyOf(loadSettings());
```

Другой вариант — создать map до запуска потока и передать её этому потоку:

```java
Map<String, String> settings = Map.copyOf(loadSettings());

Thread worker = new Thread(() -> use(settings));
worker.start();
```

Вызов `start()` создаёт happens-before связь: новый поток увидит действия, выполненные до его запуска. А просто записать ссылку в обычное поле, которое читают уже работающие потоки, недостаточно — между записью и чтением может не быть гарантии видимости.

Если конфигурация обновляется редко, можно публиковать целиком новый неизменяемый snapshot через `volatile` поле:

```java
private volatile Map<String, String> settings = Map.of();

void reload() {
    settings = Map.copyOf(loadSettings());
}
```

Запись новой ссылки в `volatile` поле безопасно публикует готовую map. Читатели увидят либо старый snapshot, либо новый целиком; синхронизировать каждый `get()` не требуется.

Immutable map (неизменяемая map) обычно проще конкурентного контейнера, если после публикации данные действительно не меняются.

## Короткое дерево выбора

```text
Map после создания не меняется?
    да → immutable map
    нет ↓

Высокая конкуренция по независимым keys?
    да → ConcurrentHashMap
    нет ↓

Нужен простой общий lock, согласованный обход
или операция над несколькими entries?
    да → synchronizedMap может подойти

Нужны сортировка и range queries под нагрузкой?
    да → ConcurrentSkipListMap

Нужна передача элементов с ожиданием?
    да → это не Map; смотри BlockingQueue
```

## Типичные ошибки

- сохранить внешнюю ссылку на backing `HashMap` и обходить wrapper;
- считать последовательность `containsKey()` + `put()` атомарной;
- итерироваться без `synchronized (map)`;
- выполнять сетевой вызов или callback, удерживая общий mutex;
- выбирать wrapper для горячего высоконагруженного реестра;
- использовать изменяемую map, когда достаточно immutable snapshot.

## Упражнение

Создай реестр из двадцати настроек и реализуй метод согласованного snapshot через `synchronizedMap`. Затем добавь имитацию медленного форматирования и перенеси её за пределы `synchronized`, чтобы общий lock защищал только копирование.

> **Главная мысль:** `synchronizedMap` выбирают для небольшой map с низкой конкуренцией, когда нужен простой общий mutex, согласованный snapshot или произвольная операция над несколькими entries. Для частого независимого доступа по ключам обычно лучше `ConcurrentHashMap`, для producer–consumer — `BlockingQueue`, а для неизменяемых данных — immutable map.
