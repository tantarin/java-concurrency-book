# wait(), notify() и notifyAll(): ожидание условия

> Как потоки координируются через монитор объекта

← [Где прячется lock у метода](./09-synchronized-method.md) · [Почему изменения нужно «увидеть»](./10-visibility.md) →

## Задача перед теорией: ограниченный буфер

Producer (производитель) кладёт задания в буфер, а consumer (потребитель) забирает их. Вместимость буфера — десять элементов.

- consumer не может взять элемент из пустого буфера;
- producer не может добавить элемент в заполненный буфер;
- поток должен ждать, не расходуя процессор на бесконечную проверку.

Плохой вариант — busy waiting (активное ожидание):

```java
while (buffer.isEmpty()) {
    // снова и снова занимает CPU проверкой
}
```

Можно вставить `Thread.sleep()`, но поток будет просыпаться либо слишком часто, либо с лишней задержкой. Кроме того, изменение буфера никак не сообщает спящему потоку: «условие уже изменилось».

Нужна coordination (координация): поток приостанавливается до изменения защищённого состояния. На низком уровне Java это позволяют сделать `wait()`, `notify()` и `notifyAll()`.

## Карта способов ожидания

| Инструмент | Что выражает | Когда выбирать |
|---|---|---|
| `wait/notify` | собственный протокол условия поверх монитора | обучение или низкоуровневый компонент с аккуратно заданным инвариантом |
| `Condition` | одно или несколько именованных условий вместе с `Lock` | нужен явный lock и отдельные очереди условий |
| `BlockingQueue` | готовая блокирующая передача элементов | producer–consumer в прикладном коде |
| `CountDownLatch` | ожидание конечного числа событий | одноразовый барьер готовности |

Для настоящей очереди обычно берут `BlockingQueue`. Здесь реализуем маленький буфер вручную, чтобы увидеть механику монитора.

## Почему методы находятся в Object

Методы объявлены в `java.lang.Object`:

```java
public final void wait() throws InterruptedException;
public final native void notify();
public final native void notifyAll();
```

Каждый объект Java может служить монитором, поэтому ожидание связано не с классом `Thread`, а с конкретным объектом-lock. Вызов:

```java
lock.wait();
```

означает: «текущий поток ждёт изменения условия, защищённого монитором `lock`».

Это instance methods (методы экземпляра), а не static methods. Поток вызывает их у того же объекта, монитор которого он захватил.

## Главное требование: владеть тем же монитором

Правильно:

```java
synchronized (lock) {
    lock.wait();
}
```

Неправильно:

```java
lock.wait(); // IllegalMonitorStateException
```

И так тоже неправильно:

```java
synchronized (lockA) {
    lockB.wait(); // монитор lockB не захвачен
}
```

`wait()`, `notify()` и `notifyAll()` требуют владения монитором именно объекта-получателя. Иначе JVM бросает `IllegalMonitorStateException`.

Причина в том, что условие нельзя безопасно проверять отдельно от перехода к ожиданию. Оба действия должны происходить под одним монитором, иначе уведомление может попасть в промежуток и потеряться.

## Что именно делает wait()

Пусть consumer обнаружил пустой буфер:

```java
synchronized (lock) {
    while (buffer.isEmpty()) {
        lock.wait();
    }
    return buffer.remove();
}
```

`wait()` атомарно выполняет связку действий:

1. добавляет текущий поток в wait set (набор ожидающих) объекта `lock`;
2. освобождает монитор `lock`;
3. приостанавливает поток;
4. после пробуждения снова захватывает монитор `lock`;
5. только затем возвращает управление из `wait()`.

Освобождение монитора принципиально. Если бы consumer продолжал удерживать `lock`, producer не смог бы войти в `synchronized`, положить элемент и изменить условие.

`wait()` освобождает только монитор объекта, у которого он вызван. Другие захваченные потоком мониторы автоматически не освобождаются.

## Что делают notify() и notifyAll()

После добавления элемента producer сообщает, что состояние изменилось:

```java
synchronized (lock) {
    buffer.add(element);
    lock.notifyAll();
}
```

`notify()` пробуждает один произвольно выбранный поток из wait set этого объекта. Нельзя потребовать, чтобы это был самый старый consumer или конкретный поток.

`notifyAll()` пробуждает все потоки из wait set. Но они не продолжают работу одновременно: каждому ещё нужно снова захватить тот же монитор.

Важно: уведомляющий поток не освобождает монитор в момент вызова `notify()` или `notifyAll()`. Он продолжает выполнять синхронизированный блок. Пробуждённые потоки смогут войти только после его выхода.

```text
producer держит monitor
    ├── изменяет состояние
    ├── notifyAll()
    ├── всё ещё держит monitor
    └── выходит из synchronized → monitor освобождён
                                 → один из проснувшихся захватывает его
```

Уведомление означает не «условие истинно», а только «состояние могло измениться».

## Почему wait() всегда находится в while

Правильный guarded block (блок, защищённый условием):

```java
synchronized (lock) {
    while (!condition) {
        lock.wait();
    }
    useState();
}
```

Не следует заменять `while` на `if`:

```java
if (!condition) {
    lock.wait();
}
```

После пробуждения условие проверяют заново по трём причинам:

- другой проснувшийся поток мог первым захватить монитор и изменить состояние;
- `notifyAll()` будит потоки, ожидающие разных условий;
- разрешено spurious wakeup (ложное пробуждение) без подходящего уведомления.

Цикл не является активным ожиданием: когда условие ложно, `wait()` снова приостанавливает поток и освобождает монитор.

## notify() или notifyAll()

В ограниченном буфере на одном мониторе ждут две разные группы:

- producers ждут `size < capacity`;
- consumers ждут `size > 0`.

Если вызвать `notify()`, JVM может разбудить поток, для которого условие всё ещё ложно. Например, после извлечения элемента можно случайно разбудить другого consumer вместо producer. При сложном протоколе это может оставить полезную работу без подходящего пробуждения.

`notifyAll()` безопаснее: все перепроверят свои условия в `while`, а продолжат только те, кому состояние подходит. Цена — лишние пробуждения и конкуренция за монитор.

Практическое правило:

- используй `notifyAll()`, если один wait set обслуживает разные условия или корректность `notify()` трудно доказать;
- `notify()` допустим, когда все ожидающие эквивалентны и одно изменение позволяет продолжить ровно одному потоку;
- если разные условия важны для производительности, рассмотри несколько `Condition`, а не усложняй неявный wait set.

## Ограниченный буфер целиком

```java
public synchronized void put(E element) throws InterruptedException {
    while (size == elements.length) {
        wait();
    }
    add(element);
    notifyAll();
}

public synchronized E take() throws InterruptedException {
    while (size == 0) {
        wait();
    }
    E element = remove();
    notifyAll();
    return element;
}
```

Методы синхронизированы на `this`, поэтому вызовы без получателя:

```java
wait();
notifyAll();
```

эквивалентны `this.wait()` и `this.notifyAll()`. Состояние `size`, проверка условия, изменение и уведомление защищены одним монитором.

## InterruptedException

`wait()` — прерываемое ожидание. Если другой поток вызывает `waitingThread.interrupt()`, ожидающий поток выходит через `InterruptedException` после повторного захвата монитора.

Поэтому методы буфера честно объявляют:

```java
E take() throws InterruptedException
```

Не следует молча проглатывать прерывание. Вызывающий код должен либо передать исключение выше, либо восстановить флаг через `Thread.currentThread().interrupt()` и завершить свою работу по принятому протоколу.

Есть варианты `wait(long timeout)` и `wait(long timeout, int nanos)`. Таймаут ограничивает длительность одного ожидания, но после возврата условие всё равно проверяется в `while`.

## wait() и sleep() — не одно и то же

| `wait()` | `Thread.sleep()` |
|---|---|
| метод объекта | static method класса `Thread` |
| используется для ожидания условия | задерживает текущий поток на время |
| должен вызываться при владении монитором объекта | не требует монитора |
| освобождает монитор объекта | не освобождает захваченные мониторы |
| может завершиться после уведомления | уведомления монитора на него не действуют |

`sleep()` не заменяет протокол состояния и уведомления.

## Связь с видимостью

Пробуждённый поток не продолжает работу, пока снова не захватит монитор. Изменение состояния выполняется до выхода уведомляющего потока из `synchronized`, а чтение — после захвата того же монитора. Поэтому монитор участвует не только во взаимном исключении, но и в публикации изменений.

Почему это даёт гарантию видимости, последовательно разберём в главах про [visibility](./10-visibility.md) и [happens-before](./12-happens-before.md).

## Типичные ошибки

- вызвать `wait()` или `notifyAll()` вне `synchronized`;
- ждать на одном объекте, а уведомлять другой;
- проверять условие через `if`, а не `while`;
- вызвать `notify()` до изменения защищённого состояния;
- считать, что `notifyAll()` немедленно передаёт управление ожидающим;
- проглотить `InterruptedException`;
- вручную писать очередь, когда контракт уже предоставляет `BlockingQueue`.

## Упражнение

Добавь в учебный буфер метод `take(long timeout, TimeUnit unit)`. Он должен корректно учитывать время, потраченное на повторные пробуждения, а не начинать полный таймаут заново после каждого `wait()`.

> **Главная мысль:** `wait()` атомарно освобождает монитор и приостанавливает поток до возможного изменения условия. После пробуждения поток снова захватывает монитор и обязательно перепроверяет условие в `while`. `notifyAll()` лишь сообщает об изменении состояния — оно не передаёт монитор и не гарантирует, что условие уже истинно.
