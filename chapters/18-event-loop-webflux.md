# Event loop в WebFlux: один диспетчер, много запросов

> Как обслуживать много ожидающих I/O-операций небольшим числом потоков

← [Виртуальные потоки в Java](./18-virtual-threads.md) · [Как рассуждать о многопоточном коде](./19-reasoning-about-concurrency.md) →

## Задача перед теорией: сервис статусов заказов

Представь WebFlux-сервис. Клиенты запрашивают статусы заказов, а сервис обращается к другому HTTP-сервису:

```java
@GetMapping("/orders/{id}")
Mono<Order> getOrder(@PathVariable long id) {
    return webClient.get()
        .uri("http://orders/{id}", id)
        .retrieve()
        .bodyToMono(Order.class);
}
```

Одновременно приходят тысячи запросов. Ответ удалённого сервиса занимает 100–500 ms, но процессору нашего приложения почти нечего делать во время ожидания.

В модели thread-per-request (поток на запрос) каждый запрос мог бы удерживать отдельный поток всё время:

```text
request 1 → thread 1 → ждёт сеть
request 2 → thread 2 → ждёт сеть
request 3 → thread 3 → ждёт сеть
```

WebFlux с неблокирующим сервером использует другую модель: небольшое фиксированное число event loop threads обслуживает много соединений.

## Модель на пальцах: заказчики, диспетчер и исполнители

Начнём с упрощённой картины:

- N заказчиков отправляют поручения;
- event loop (цикл обработки событий) работает как диспетчер;
- M исполнителей выполняют то, чего диспетчер не может сделать мгновенно;
- диспетчер принимает готовые результаты и возвращает их нужным заказчикам.

```text
заказчики                 исполнители

request A ─┐             ┌→ HTTP-сервис
request B ─┼→ event loop ├→ база данных
request C ─┘             └→ файловая система
               ↑                │
               └── события готовности
```

Главное правило диспетчера: **не стоять и не ждать одного исполнителя**. Передав поручение, он сразу занимается следующим событием.

Однако метафору нужно уточнить. В WebFlux исполнители — это не обязательно M Java-потоков из пула. При неблокирующем сетевом I/O работу выполняют удалённый сервис, сетевое устройство и операционная система. Event loop регистрирует интерес к результату, а ОС позже сообщает: сокет готов к чтению или записи.

## Что такое event loop

Event loop (цикл обработки событий) — это поток, который многократно выполняет короткий цикл:

```text
пока приложение работает:
    получить готовые события
    выполнить короткие обработчики
    зарегистрировать следующие I/O-операции
    перейти к другим готовым событиям
```

Событием может быть:

- установлено новое соединение;
- из сокета можно прочитать HTTP-запрос;
- пришла часть ответа от удалённого сервиса;
- в сокет можно записать ответ клиенту;
- сработал timer (таймер);
- завершился callback (обратный вызов).

Один event loop thread выполняет обработчики последовательно. В каждый конкретный момент он исполняет код только одного события, но за время ожидания I/O успевает продвинуть множество разных запросов.

```text
время →

event-loop-1:
request A: принять ─ request B: принять ─ request C: продолжить ─ request A: продолжить
                   A ждёт сеть ────────────────┘
```

Поэтому точнее говорить не «все операции выполняются одновременно на одном потоке», а так:

> Один физический поток по очереди выполняет короткие участки множества запросов и не занят, пока их I/O выполняется вне этого потока.

## Полный путь одного запроса

Рассмотрим запрос `GET /orders/42` по шагам.

### 1. Клиент прислал запрос

Операционная система сообщает Reactor Netty, что в сокете появились данные. Event loop читает запрос и вызывает WebFlux handler.

```text
client A → данные готовы → event loop → getOrder(42)
```

### 2. Handler описал асинхронную операцию

Метод возвращает `Mono<Order>` — описание результата, который появится позже:

```java
Mono<Order> order = webClient.get()
    .uri("http://orders/{id}", 42)
    .retrieve()
    .bodyToMono(Order.class);
```

`Mono` не является отдельным потоком и сам ничего не исполняет. Это publisher (издатель), который описывает, как получить от нуля до одного результата и что делать с сигналами результата, ошибки или завершения.

### 3. WebClient начал неблокирующий I/O

`WebClient` инициирует HTTP-запрос и регистрирует сетевую операцию. Event loop не ждёт ответ внутри вызова:

```text
event loop → отправил запрос orders-service
event loop → вернулся к другим событиям

orders-service обрабатывает запрос...
```

В это время тот же event loop может принять запросы B, C и D. Для каждого запроса сохраняется его собственная reactive chain (реактивная цепочка), поэтому результат не потеряется и вернётся нужному клиенту.

### 4. Ответ стал доступен

Когда данные приходят, операционная система сообщает о готовности сокета. Event loop читает ответ и продолжает цепочку именно запроса A:

```text
orders-service → данные готовы → event loop
event loop → декодировать Order → отправить response клиенту A
```

Event loop не проверяет каждый запрос в бесконечном Java-цикле. Он опирается на механизм уведомлений операционной системы о готовности I/O.

## Где здесь N и M

В исходной метафоре:

```text
N заказчиков → event loop → M исполнителей
```

соответствия такие:

| Метафора | В WebFlux с Reactor Netty |
|---|---|
| N заказчиков | клиентские HTTP-соединения и запросы |
| диспетчер | event loop thread |
| поручение | короткий обработчик события или запуск I/O |
| исполнители | удалённые сервисы, БД, сеть и ОС; иногда отдельный Scheduler |
| готовый результат | событие готовности сокета и сигнал `onNext`, `onError` или `onComplete` |
| вернуть заказчику | продолжить цепочку запроса и записать HTTP-response в его соединение |

Число заказчиков может быть гораздо больше числа event loop threads. Но в реальном WebFlux-приложении обычно работает не один event loop на весь сервер, а небольшая event loop group (группа циклов обработки событий). Reactor Netty по умолчанию создаёт фиксированное число I/O workers, связанное с числом доступных процессоров.

Каждое соединение закрепляется за одним event loop, а один event loop обслуживает много соединений:

```text
connections A, C, E ─→ event-loop-1
connections B, D, F ─→ event-loop-2
connections G, H    ─→ event-loop-3
```

## Почему это называется неблокирующей моделью

Blocking operation (блокирующая операция) удерживает вызывающий поток, пока результат не появится:

```java
Order order = blockingClient.loadOrder(id); // поток ждёт
return order;
```

Non-blocking operation (неблокирующая операция) запускает работу и позволяет потоку заняться другими событиями. Результат продолжит цепочку позже:

```java
return webClient.get()
    .uri("http://orders/{id}", id)
    .retrieve()
    .bodyToMono(Order.class);
```

Неблокирующий код не означает, что результат появляется без ожидания. Клиент по-прежнему ждёт ответ 300 ms. Разница в том, что Java-поток не простаивает все эти 300 ms.

```text
blocking:
thread A → отправил → [ждёт 300 ms] → получил

non-blocking:
event loop → отправил A → обслужил B → обслужил C → продолжил A
```

Это обычно не уменьшает latency (задержку) конкретного удалённого вызова. Преимущество — throughput (пропускная способность): небольшое число потоков может держать много одновременно ожидающих операций.

## Что произойдёт, если заблокировать event loop

Главная опасность WebFlux — выполнить долгую или блокирующую работу прямо на event loop:

```java
@GetMapping("/orders/{id}")
Mono<Order> getOrder(@PathVariable long id) {
    Thread.sleep(1_000); // блокирует event loop
    return Mono.just(loadOrder(id));
}
```

Пока поток спит, он не обрабатывает события остальных закреплённых за ним соединений:

```text
event-loop-1 → request A: sleep(1 s)
               request B: ждёт event loop
               request C: ждёт event loop
               request D: ждёт event loop
```

Так один медленный handler задерживает не только свой запрос. Он останавливает продвижение многих запросов на том же loop.

Опасны, например:

- `Thread.sleep()`;
- обычный JDBC и JPA;
- синхронный HTTP-клиент;
- долгое чтение файла блокирующим API;
- тяжёлое CPU-вычисление;
- вызовы `Mono.block()` и `Future.get()` на event loop.

## Что делать с блокирующим API

Лучший вариант — использовать неблокирующий API на всём пути: например, `WebClient` для HTTP и reactive driver (реактивный драйвер) для базы данных.

Если отказаться от блокирующей библиотеки пока нельзя, работу можно явно перенести на предназначенный для этого `Scheduler`:

```java
Mono<Order> order = Mono.fromCallable(
        () -> blockingRepository.loadOrder(id)
    )
    .subscribeOn(Schedulers.boundedElastic());
```

Теперь блокирующий вызов занимает отдельный worker thread, а event loop остаётся свободным. Но это уже компромисс: физический поток всё-таки блокируется, появляется очередь и нужно контролировать нагрузку. Обёртка не превращает JDBC или другой blocking API в настоящий non-blocking I/O.

```text
event loop → поставил blocking task → boundedElastic worker ждёт JDBC
event loop → обслуживает другие события
worker завершился → сигнал результата → reactive chain продолжается
```

## Event loop не является Executor в обычном смысле

У event loop действительно есть очередь задач, и он выполняет callbacks. Но полезно не представлять его как обычный `ExecutorService`, который только раздаёт все запросы свободным workers.

В типичном неблокирующем WebFlux-сценарии event loop сам выполняет короткий application code (код приложения): операторы Reactor, маршрутизацию, сериализацию и обработчики. Внешнее ожидание передаётся не Java-worker, а механизму неблокирующего I/O.

Отдельный пул появляется только там, где мы сознательно переключили выполнение через `publishOn()` или `subscribeOn()`, либо используем библиотеку со своими потоками.

## Сравнение трёх моделей

| Модель | Что представляет ожидающий запрос | Что происходит при I/O |
|---|---|---|
| Spring MVC + platform threads | один request thread | platform thread блокируется |
| WebFlux + event loop | состояние reactive chain | event loop освобождён и обрабатывает другие события |
| Virtual thread per request | один дешёвый virtual thread | virtual thread обычно освобождает carrier thread |

WebFlux и virtual threads решают похожую проблему разными способами:

- WebFlux сохраняет мало потоков, но требует неблокирующих API и реактивной композиции;
- virtual threads позволяют писать последовательный блокирующий код, а JDK переносит ожидающие virtual threads между carrier threads.

WebFlux не становится автоматически лучшим выбором только из-за большого числа запросов. Если зависимости блокирующие, а команда пишет обычный императивный код, Spring MVC с virtual threads может оказаться проще. Решение принимают по всей цепочке I/O, профилю нагрузки и сложности разработки.

## Короткая проверка модели

### Верно

```text
много соединений
→ небольшая группа event loops
→ короткие обработчики
→ неблокирующий I/O
→ событие готовности
→ продолжение нужной reactive chain
```

### Неверно

```text
один event loop
→ раздал каждый HTTP-request потоку из большого пула
→ поток ждёт результат
```

Это уже ближе к классической модели thread pool, а не к главному преимуществу event loop.

## Упражнение

Возьми WebFlux-handler, который вызывает два удалённых HTTP-сервиса через `WebClient`. Нарисуй timeline для двух одновременных клиентских запросов: отметь короткие участки работы event loop и интервалы, когда ответы ожидаются без занятого Java-потока. Затем добавь в handler `Thread.sleep(1000)` и объясни, какие запросы он задержит.

> **Главная мысль:** event loop не выделяет поток на каждый ожидающий запрос. Небольшое число физических потоков по очереди выполняет короткие обработчики множества соединений, регистрирует неблокирующий I/O и продолжает нужную цепочку после события готовности. Поэтому event loop нельзя блокировать.
