# Race condition: когда результат зависит от порядка потоков

> Гонки, data race и способы исправления

← [Как теряется инкремент](./05-race-condition.md) · [Mutex: один ключ от комнаты](./06-mutex.md) →

**Race condition**, или состояние гонки, — ошибка проектирования, при которой правильность результата зависит от относительного порядка или времени выполнения нескольких операций.

В однопоточной программе следующий шаг известен. В многопоточной программе действия могут перемешиваться:

```text
Thread 1: прочитать значение
Thread 2: прочитать значение
Thread 1: изменить и записать
Thread 2: изменить и записать
```

Если один допустимый порядок даёт правильный результат, а другой допустимый порядок ломает требование программы, перед нами race condition.

## Потерянное обновление

Операция `count++` состоит из нескольких действий:

```java
int oldValue = count;
int newValue = oldValue + 1;
count = newValue;
```

Два потока могут прочитать одинаковое старое значение и оба записать одинаковый результат. Исключения не возникнет, но одно обновление потеряется.

```text
начало: count = 10

Thread 1 читает 10
Thread 2 читает 10
Thread 1 пишет 11
Thread 2 пишет 11

ожидали: 12
получили: 11
```

Это пример операции **read-modify-write**: прочитать, вычислить, записать. Вся последовательность должна иметь одну границу атомарности.

## Check-then-act

Другая распространённая гонка возникает между проверкой и действием:

```java
if (!users.containsKey(id)) {
    users.put(id, loadUser(id));
}
```

`Thread 1` и `Thread 2` могут одновременно обнаружить, что ключа нет, а затем оба загрузить и записать пользователя. Даже если отдельные `containsKey()` и `put()` потокобезопасны, их композиция не становится одной атомарной операцией.

Для `ConcurrentHashMap` намерение можно выразить одной составной операцией:

```java
users.computeIfAbsent(id, this::loadUser);
```

## Race condition и data race — не полные синонимы

Термины часто используют как синонимы, но между ними есть различие.

**Data race** в терминах Java Memory Model возникает, когда два потока обращаются к одной переменной, хотя бы одно обращение является записью и эти конфликтующие обращения не упорядочены отношением happens-before.

**Race condition** — более широкая логическая проблема: результат зависит от порядка событий. Она возможна даже при использовании потокобезопасных методов, если несколько таких вызовов должны были образовывать одну операцию.

Например, методы `containsKey()` и `put()` у конкурентной Map безопасны по отдельности. Но последовательность «проверить, затем добавить» всё равно может содержать race condition.

## Почему гонку трудно заметить

Планировщик не обязан каждый раз одинаково переключать потоки. Поэтому программа может:

- сто раз завершиться правильно;
- сломаться только под нагрузкой;
- перестать воспроизводить ошибку после добавления логирования;
- вести себя по-разному на другом процессоре или JVM.

Один удачный запуск ничего не доказывает. `Thread.sleep()` также не исправляет гонку: он меняет вероятный порядок, но не создаёт необходимой гарантии.

## Как исправлять race condition

Сначала нужно сформулировать, какие действия являются одной логической операцией. После этого выбирают подходящий способ:

1. **Не делить состояние** — оставить данные внутри одного потока.
2. **Сделать данные immutable** — после создания их нельзя изменить.
3. **Использовать атомарную операцию** — например `AtomicInteger.incrementAndGet()`.
4. **Защитить всю составную операцию одним lock** — а не отдельные её строки разными блокировками.
5. **Использовать готовый составной метод** — `compute`, `merge`, `putIfAbsent`.
6. **Передавать задачи через очередь** — состояние изменяет один выделенный consumer.

Средство выбирают не по названию класса, а по требуемой границе атомарности.

## Вопросы для проверки кода

При поиске гонки задай вопросы:

1. Какие данные доступны нескольким потокам?
2. Может ли хотя бы один поток изменить их?
3. Какое бизнес-действие должно выполняться целиком?
4. Может ли другой поток вклиниться между проверкой и действием?
5. Что создаёт happens-before между записью и чтением?
6. Покрывает ли lock всю операцию или только отдельный метод?

> **Главная мысль:** race condition определяется не наличием нескольких потоков само по себе, а нарушенным требованием программы при одном из допустимых порядков их действий.
