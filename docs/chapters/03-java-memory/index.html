Где JVM хранит данные: stack, heap и не только

Области памяти Java-процесса

← Что такое поток · Наш сервис просмотров →

Когда запускается Java-приложение, операционная система создаёт процесс и выделяет ему память. JVM использует эту память не как один сплошной склад, а делит её на области с разным назначением.

Java-процесс
│
├── Heap                         общая для потоков
├── Metaspace                    общая для потоков
├── Code Cache                   общая для потоков
├── Direct / native memory       общая для потоков
│
├── Stack потока 1               принадлежит потоку 1
├── Stack потока 2               принадлежит потоку 2
└── Stack потока 3               принадлежит потоку 3

Stack: память выполнения метода

У каждого потока свой stack (стек вызовов). Когда поток вызывает метод, JVM создаёт для него stack frame (кадр стека). В нём находятся параметры метода, локальные переменные и служебные данные для возврата к вызывающему коду.

void showCar() {
    int page = 1;                    // значение находится в frame
    Car car = repository.find(42);  // ссылка находится в frame
}

Переменная car — локальная ссылка в стеке текущего потока. Сам объект Car обычно находится в heap. Когда метод завершается, его frame удаляется со стека.

Другой поток не получает прямой доступ к stack frame первого потока. Поэтому обычная локальная переменная безопасна, пока ссылка на связанный с ней объект не передана наружу.

Слишком глубокая рекурсия может заполнить стек и привести к StackOverflowError.

Heap: память объектов

Heap (куча) — общая область, в которой JVM обычно размещает объекты и массивы:

ViewCounter counter = new ViewCounter();

Локальная переменная counter находится в stack frame выполняющего потока, а созданный ViewCounter — в heap. Несколько потоков могут хранить ссылки на один объект:

Thread 1 stack ──┐
                 ├──→ один ViewCounter в heap
Thread 2 stack ──┘

Именно поэтому появляется проблема общего изменяемого состояния. Heap сам по себе не делает объект опасным: проблема возникает, когда несколько потоков получили один объект и хотя бы один из них его изменяет.

Объекты, которые больше недостижимы по ссылкам, может удалить garbage collector. Если heap заполнен и сборщик не может освободить достаточно места, приложение получает OutOfMemoryError: Java heap space.

Metaspace: описание классов

JVM должна хранить сведения о загруженных классах: их структуру, методы и другую метаинформацию. В HotSpot эта область называется Metaspace (область метаданных) и использует native memory (нативную память вне Java heap).

ViewCounter.class → описание класса в Metaspace
new ViewCounter() → экземпляр класса в Heap

Объект класса и экземпляр класса — не одно и то же. Поэтому ошибка OutOfMemoryError: Metaspace отличается от переполнения heap.

Code Cache и память вне heap

JIT-компилятор превращает часто выполняемый байткод в машинные инструкции и хранит их в Code Cache (кеше скомпилированного кода).

Java-процесс также использует память вне heap:

  • native-библиотеки и внутренние структуры JVM;
  • стеки потоков;
  • direct buffers, созданные через ByteBuffer.allocateDirect();
  • memory-mapped файлы;
  • структуры garbage collector и JIT.

Поэтому параметр -Xmx ограничивает только максимальный размер heap, а не всю память процесса. Процесс может занимать больше памяти, чем указано в -Xmx.

Что важно для многопоточности

Упрощённая модель для начала курса выглядит так:

Область Общая между потоками Что обычно хранится
Stack Нет вызовы методов, локальные значения и ссылки
Heap Да объекты и массивы
Metaspace Да информация о загруженных классах
Code Cache Да скомпилированный JIT машинный код
Direct/native memory Да буферы и внутренние данные JVM

Главная мысль: локальная ссылка может находиться в стеке одного потока, но указывать на объект в общей heap-памяти. Потокобезопасность определяется тем, кто получил доступ к объекту и может ли его изменить.
