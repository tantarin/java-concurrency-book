Deadlock vs. livelock: нет прогресса по разным причинам

Потоки заблокированы или активно мешают друг другу

← synchronized vs. ReentrantLock · Почему изменения нужно «увидеть» →

Задача перед теорией: два встречных перевода

Два потока одновременно переводят деньги между счетами:

Thread 1: Account A → Account B
Thread 2: Account B → Account A

Чтобы перевод был целостным, нужно заблокировать оба счёта. Наивная реализация сначала захватывает исходный счёт, затем целевой:

void transfer(Account from, Account to, long amount) {
    synchronized (from) {
        synchronized (to) {
            from.withdraw(amount);
            to.deposit(amount);
        }
    }
}

Возможен порядок:

Thread 1 захватил A и ждёт B
Thread 2 захватил B и ждёт A

Оба потока могут ждать бесконечно. Это deadlock (взаимная блокировка).

Разработчик пробует «исправление»: если второй lock занят, освободить первый и немедленно повторить. Теперь потоки не заблокированы — они постоянно захватывают, проверяют и освобождают locks. Но при одинаковом ритме оба каждый раз уступают одновременно, и перевод всё равно не выполняется. Это livelock (активная взаимная блокировка).

Симптом один — полезная операция не завершается. Механика принципиально разная.

Общее понятие: liveness

Liveness (живость, способность системы продвигаться) отвечает на вопрос: «произойдёт ли когда-нибудь нужное событие?»

Потокобезопасный код должен заботиться не только о safety (безопасности: ничего плохого не произойдёт), но и о прогрессе:

safety   → баланс не повреждён
liveness → перевод когда-нибудь завершится

Deadlock, livelock и starvation (голодание) — разные liveness failures (нарушения живости).

Проблема Состояние потоков Почему нет прогресса
Deadlock ждут ресурсы друг друга образован цикл ожидания
Livelock выполняются и меняют состояние реакции потоков взаимно отменяют прогресс
Starvation один поток постоянно проигрывает конкуренцию ресурс достаётся другим потокам

Deadlock: цикл ожидания

Deadlock возникает не просто потому, что есть два locks. Для классической взаимной блокировки одновременно складываются четыре условия:

  1. mutual exclusion (взаимное исключение) — ресурсом владеет один поток;
  2. hold and wait (удержание и ожидание) — поток удерживает один ресурс и ждёт другой;
  3. no preemption (нет принудительного изъятия) — чужой lock нельзя просто отобрать;
  4. circular wait (циклическое ожидание) — цепочка ожиданий замыкается.
Thread 1 держит A ──ждёт──→ B
      ↑                         │
      └──── A ←──ждёт── Thread 2 держит B

Для предотвращения достаточно гарантированно разрушить хотя бы одно условие. На практике чаще всего исключают цикл единым порядком захвата locks.

Исправление: глобальный порядок locks

Каждому счёту назначен неизменяемый id. Независимо от направления перевода сначала захватывается счёт с меньшим id:

Account first = from.id() < to.id() ? from : to;
Account second = from.id() < to.id() ? to : from;

synchronized (first) {
    synchronized (second) {
        transferMoney(from, to, amount);
    }
}

Теперь оба встречных перевода запрашивают locks в порядке A → B. Один поток может ждать, но цикл A → B → A невозможен.

Порядок должен быть:

  • глобальным — одинаковым во всех местах программы;
  • стабильным — ключ порядка не изменяется во время операции;
  • полным — нужно определить порядок и для разных объектов с одинаковыми бизнес-значениями.

Другие способы уменьшить риск deadlock

  • не удерживать несколько locks одновременно;
  • уменьшать область блокировки и не вызывать неизвестный внешний код под lock;
  • объединить тесно связанное состояние под одним lock;
  • использовать tryLock(timeout, unit) и корректно освобождать уже полученные locks;
  • использовать lockInterruptibly(), если протокол допускает отмену ожидания;
  • проектировать обмен через очереди или неизменяемые сообщения вместо совместного владения.

Таймаут только позволяет выйти из ожидания. Он не доказывает, что операция будет завершена при следующей попытке.

У входа в synchronized нет API с таймаутом и обычное ожидание intrinsic lock (встроенного lock объекта) нельзя прервать. Если нужны такие политики, рассматривают ReentrantLock.

Livelock: активность без результата

Представь двух людей в узком коридоре:

оба шагнули влево
оба увидели помеху и шагнули вправо
оба снова увидели помеху и шагнули влево

Они не стоят: постоянно реагируют друг на друга. Но расстояние до цели не уменьшается.

Аналогичная ошибка с tryLock():

while (!transferred) {
    first.lock();
    try {
        if (second.tryLock()) {
            try {
                transferMoney();
                transferred = true;
            } finally {
                second.unlock();
            }
        }
    } finally {
        first.unlock();
    }
}

Код не блокируется навсегда на втором lock, но симметричные потоки могут бесконечно повторять одинаковые неудачные действия.

Как разрушить livelock

Нужно убрать идеальную симметрию или бесконечную взаимную реакцию:

  • ввести единый порядок захвата locks — для переводов это лучше повторов;
  • использовать bounded retries (ограниченное число повторов), после которого операция явно завершается ошибкой;
  • добавить backoff (увеличивающуюся паузу между попытками);
  • добавить jitter (случайный разброс задержки), чтобы потоки не повторяли шаги синхронно;
  • назначить приоритет или одного координатора;
  • блокировать операцию на уровне очереди, вместо того чтобы всем участникам немедленно уступать.

Случайная задержка снижает вероятность повторной синхронизации, но не заменяет доказуемый протокол, если можно задать порядок ресурсов.

Главное различие

Deadlock
Thread 1: BLOCKED, ждёт B
Thread 2: BLOCKED, ждёт A
CPU почти не используется

Livelock
Thread 1: захватил → проверил → отпустил → повторил
Thread 2: захватил → проверил → отпустил → повторил
CPU используется, полезного результата нет

Состояние RUNNABLE или BLOCKED помогает диагностике, но само по себе не является доказательством. Важен граф владения ресурсами и изменение бизнес-метрики прогресса.

Как обнаружить deadlock

JVM умеет находить циклы владения мониторами и ownable synchronizers (синхронизаторами владения, например ReentrantLock):

ThreadMXBean threads = ManagementFactory.getThreadMXBean();
long[] ids = threads.findDeadlockedThreads();

Для работающего процесса полезен thread dump (дамп потоков). Его можно получить, например, через:

jcmd <pid> Thread.print

В дампе ищут:

  • какие locks удерживает каждый поток;
  • какой lock он ожидает;
  • повторяющийся цикл между потоками;
  • одинаковые stack traces на протяжении нескольких снимков.

findMonitorDeadlockedThreads() ищет только циклы intrinsic monitors, а findDeadlockedThreads() также учитывает ownable synchronizers.

Почему livelock обнаруживать сложнее

При livelock нет обязательного цикла заблокированных threads. Thread dump может показывать RUNNABLE, а stack trace — постоянно меняющиеся попытки.

Нужны наблюдения во времени:

  • CPU и число попыток растут;
  • полезный счётчик завершённых операций не растёт;
  • логи повторяют один сценарий retry;
  • несколько thread dumps показывают активность в одном цикле;
  • профилировщик показывает горячий retry-loop.

Поэтому системе полезны отдельные метрики attempts, retries, failures и completed, а не только признак «поток жив».

В учебном проекте

Модуль содержит три варианта:

  • детерминированный deadlock двух monitors
  • обнаружение цикла через ThreadMXBean
  • детерминированная симуляция livelock
  • предотвращение deadlock общим порядком locks
  • тест активности без прогресса и встречных переводов

Deadlock-демонстрация создаёт daemon threads (фоновые потоки), чтобы JVM могла завершиться после обнаружения цикла. Такой приём нужен только для безопасного учебного запуска, а не для исправления production-кода.

Типичные ошибки

  • считать любой зависший запрос deadlock: причиной может быть медленный I/O, starvation или потерянное уведомление;
  • лечить deadlock бесконечным tryLock() без backoff и получить livelock;
  • вводить порядок locks только в одном методе, оставляя обратный порядок в другом;
  • использовать таймаут как замену корректному освобождению ресурсов;
  • анализировать один thread dump без сравнения во времени;
  • считать высокую активность CPU доказательством полезного прогресса.

Упражнение

Добавь третий счёт и запусти переводы A → B, B → C и C → A одновременно. Сначала продемонстрируй цикл при порядке «from, затем to», затем используй сортировку по id и проверь с таймаутом, что все операции завершаются.

Главная мысль: при deadlock потоки ждут ресурсы по замкнутому циклу; при livelock они продолжают выполнять код, но их реакции не дают полезного прогресса. Единый порядок ресурсов предотвращает цикл, а ограниченные повторы, backoff и асимметрия помогают не превратить ожидание в бесконечную суету.
